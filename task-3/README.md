# Task3 — Анализ проблем и рисков текущей архитектуры

## 1. Проблемы синхронных REST-взаимодействий

- Высокая связность между сервисами.
- Зависимость от доступности и скорости работы внешних страховых компаний.
- Каждое обращение к `ins-product-aggregator` требует актуального обращения к страховым.
- При росте числа партнеров возрастает RPS и время отклика.
- Задержки и тайм-ауты при интеграциях ведут к деградации работы всей цепочки.

## 2. Проблемы периодической синхронизации

- `core-app` опрашивает `ins-product-aggregator` раз в 15 минут.
- `ins-comp-settlement` опрашивает `ins-product-aggregator` и `core-app` раз в сутки.
- При росте объема данных возрастает нагрузка в пиковые интервалы синхронизации.
- Потенциальная несогласованность данных (на момент опроса данные могли устареть).
- Нет гарантий, что `ins-comp-settlement` всегда получает актуальные данные.

## 3. Риски при росте числа интеграций

- Планируется подключение ещё 5 страховых компаний.
- Каждая новая компания увеличивает нагрузку на синхронные запросы.
- Увеличивается вероятность ошибок из-за таймаутов, сбоев и нестабильной работы API партнеров.
- Сложность масштабирования под растущую нагрузку.
- Риск лавинообразных отказов из-за зависимостей между сервисами.

## 4. Отсутствие события изменений данных

- Нет реактивного обновления данных.
- Даже при наличии новых продуктов данные появляются у `core-app` и `ins-comp-settlement` с задержкой.
- Пользователь может не видеть актуальные тарифы в реальном времени.

## 5. Финансовые и репутационные риски

- Нарушение SLA при увеличении нагрузки.
- Потеря клиентов при задержках в оформлении страховок.
- Упущенные продажи из-за устаревших данных.
- Репутационные потери при повторных инцидентах с доступностью.

---

## Общий вывод:

- Текущая архитектура не масштабируется для дальнейшего роста бизнеса.
- Требуется переход к событийной архитектуре (Event-Driven) с использованием брокера сообщений.
- Необходимо применять паттерн `Transactional Outbox` для консистентного формирования событий.
